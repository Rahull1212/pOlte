# ARC-004.0 — Enterprise Data Strategy

| | |
|---|---|
| **Status** | Draft |
| **Phase** | 2 — Enterprise Data & Intelligence Architecture |
| **Depends on** | Phase 1 (`docs/campaign-management-design.md`) |
| **Governs** | ARC-004.1 → ARC-004.10 |
| **Date** | 2026-08-05 |

This is the constitution for PoliOS's data platform. Every other ARC-004.x document
inherits the decisions made here — they don't re-litigate tenancy model, storage
philosophy, or how the seven stores stay in sync; they implement this doc's decisions
for their slice of the system.

Two decisions anchor everything below, made explicitly rather than left implicit:

- **Tenancy: true multi-tenant SaaS.** PoliOS moves from "one deployment per
  customer" to one platform serving many organizations (parties, campaigns, NGOs)
  with hard row-level isolation.
- **Storage philosophy: Postgres-first, evolve under pressure.** Every one of the
  seven store roles in the target architecture starts as a Postgres extension or
  schema pattern. A store only graduates to dedicated infrastructure (Neo4j, a
  vector DB, Kafka, a columnar warehouse) when a named, measurable trigger fires —
  never speculatively.

## 1. Where PoliOS Is Today

The current system (`backend/prisma/schema.prisma`) is a single-tenant NestJS +
Prisma + Postgres monolith, plus Redis/BullMQ for queues. Concretely:

- **No tenant concept exists.** Every table — `User`, `Region`, `Campaign`,
  `Citizen`, `Grievance`, everything — implicitly belongs to one organization.
  The seed data models one state party's hierarchy (Telangana → districts →
  mandals → booths).
- **State is current-only.** Tables like `TargetAllocation`, `Task`, and
  `ExpenseRequest` are mutated in place. `AuditLog` records *that* something
  changed (`action`, `entityType`, `entityId`, `metadata` JSON) but not a replayable
  before/after timeline — it's a log, not an event store.
- **Relationships are foreign keys, not a queryable graph.** `Region.parentId`,
  `User.parentUserId`, and `TargetAllocation.parentAllocationId` each encode one
  hierarchy via self-joins. There's no general "how is X connected to Y" traversal
  across entity types.
- **No semantic memory.** `AIInsight` stores AI-generated text tied to a campaign,
  but nothing is embedded; the `AiModule` calls Claude with hand-assembled prompt
  context, not retrieved context.
- **No dedicated search, analytics, or object storage.** Reports are ad hoc
  aggregation queries (`AnalyticsModule`); `S3_*` env vars exist but are unused —
  WhatsApp media currently lands on local disk.

This is a solid operational core. Phase 2 doesn't replace it — the `Transaction
Database` box in the target diagram *is* this schema, evolved. Everything else in
this document is about what gets built around it.

## 2. Decision: Multi-Tenancy Model

**Decision:** Organization becomes the tenant root. Every table that is queried or
written within a tenant's scope carries an `organizationId` column directly —
denormalized, not derived by walking `Region.parentId` or `User.parentUserId` — so
that isolation is a single indexed predicate, not a recursive join.

**Isolation mechanism:** Postgres Row-Level Security (RLS), not just application-layer
guards. Every request sets `SET LOCAL app.current_org_id = '<org>'` at the start of
its transaction (via a Prisma middleware / interceptor); RLS policies on every
tenant-scoped table enforce `organizationId = current_setting('app.current_org_id')`
at the database level. The existing `RolesGuard` / `RegionScopeGuard` pattern
(`docs/campaign-management-design.md` §2) stays as the *authorization* layer
(can this role touch this region); RLS is the *isolation* layer underneath it
(can this connection see this org's rows at all, regardless of application bugs).
This is defense in depth: a bug in a service method can leak data across regions
inside one org, but it cannot leak across orgs.

**Isolation tiers (start shared, allow physical separation later):**

| Tier | Mechanism | When |
|---|---|---|
| Standard (default) | Shared DB, shared schema, RLS by `organizationId` | Every org, from day one |
| Dedicated schema | Same DB cluster, `CREATE SCHEMA org_<id>` | An org's data volume creates noisy-neighbor query contention |
| Dedicated database | Separate Postgres instance | Contractual/regulatory requirement for physical isolation (e.g. a government customer) |

Tiers 2 and 3 are escape hatches, not near-term work — they exist so a large
customer never forces a redesign, only a migration.

**Migration path from the current schema:**

1. Add `Organization` model.
2. Insert one row (the existing Telangana deployment becomes `Organization` #1).
3. Add `organizationId` to `User`, `Region`, `Campaign`, `Citizen`, and every other
   top-level entity; backfill from the single existing org; make it `NOT NULL`
   after backfill.
4. Add RLS policies per table, gated behind a feature flag until verified in
   staging against the backfilled data.
5. Add the session-variable middleware; verify every existing controller route
   still scopes correctly (this is where `RegionScopeGuard`'s tests earn their
   keep).

Full column-by-column detail is ARC-004.1's job. This section fixes the model so
ARC-004.1 has one way to do it, not eleven.

## 3. Decision: Storage Philosophy

**Decision:** Postgres-first. The target diagram's seven stores are seven *roles*,
not necessarily seven *systems*. Phase 2 realizes all seven inside or immediately
alongside the existing Postgres instance, using patterns that are each individually
well-understood and boring — the opposite of what "enterprise data platform" usually
implies. A dedicated system is adopted only when a specific, named trigger fires.

| Role | Phase 2 realization (Postgres-first) | Graduates to dedicated infra when… | Owning doc |
|---|---|---|---|
| Transaction DB | Current schema, evolved (multi-tenant) | Never fully replaced — it's the system of record | ARC-004.2 |
| Event Store | Append-only `events` table, partitioned by month + `organizationId` | Write throughput or retention makes partition management itself the bottleneck | ARC-004.3 |
| Knowledge Graph | Generic `entity_edges` table (`source`, `relation`, `target`, `orgId`, `validFrom/To`) + recursive CTEs | Traversal queries routinely exceed ~3 hops at interactive latency, or graph algorithms (centrality, community detection) are needed | ARC-004.4 |
| Vector DB | `pgvector` extension, HNSW index, embeddings table keyed by `(orgId, entityType, entityId, modelVersion)` | Embedding volume reaches tens of millions of rows, or managed multi-region scaling is required | ARC-004.5 |
| Object Storage | S3-compatible interface from day one (self-hosted MinIO for dev/on-prem, managed S3 in prod) — this is the one role Postgres was never right for | N/A — already the right tool | ARC-004.5 / ARC-004.6 |
| Search Index | Postgres full-text search (`tsvector` + GIN) plus `pg_trgm` for fuzzy match; multilingual (Telugu/Hindi/English) via per-language text search configs | Relevance or multilingual ranking quality outgrows Postgres FTS | ARC-004.6 |
| Analytics Warehouse | Logical-replication read replica + a dedicated `analytics` schema of materialized dimensional views, refreshed on event ingestion | Dashboard query latency degrades, or workload needs a columnar engine | ARC-004.7 |

The **Digital Twin** (ARC-004.8) is not an eighth store. It's a composition layer —
views and a read API that join current state, recent events, graph edges, and
analytics into one queryable "organization as of now" representation. Naming it as
a composition (not a database) keeps ARC-004.8 honest about what it's actually
building.

**Why Postgres-first instead of best-of-breed:** the team currently runs the whole
stack — API, Postgres, Redis — natively, without even Docker. Introducing Kafka,
Neo4j, a managed vector DB, and a warehouse simultaneously would multiply
operational surface area faster than the org's ability to run it. Every pattern
above is a well-trodden Postgres extension or schema convention; the cost of being
wrong about a *specific* store is "add that one piece of infra later," not "redo
the data model."

## 4. How Seven Stores Stay in Sync Without Kafka

The transactional outbox pattern, using infrastructure already in this repo
(`QueueModule`, BullMQ):

```
 Request → NestJS service
             │
             ▼  (single DB transaction)
     ┌───────────────────────────┐
     │ 1. Write operational row  │  (Transaction DB)
     │ 2. Insert into `events`   │  (Event Store — same transaction, so it's
     └───────────────────────────┘   never possible to save state without
             │                       the fact that it changed)
             ▼
     Postgres LISTEN/NOTIFY on `events` insert
             │
             ▼
     BullMQ worker (QueueModule) fans out, per event type:
             │
             ├─▶ Upsert `entity_edges`         (Knowledge Graph)
             ├─▶ Enqueue embedding job          (Vector DB)
             ├─▶ Update `tsvector` columns      (Search Index)
             └─▶ Increment materialized views   (Analytics Warehouse)
```

This gives at-least-once propagation from one durable write with no new
infrastructure. Each fan-out consumer is idempotent (keyed by `eventId`) so
retries are safe. `ARC-004.3` specifies the event schema and worker contracts in
full; this section only fixes the *shape* of the answer so downstream docs don't
each invent a different sync mechanism.

## 5. The Ten Principles, Operationalized

The principles from the phase overview are intentionally abstract. Here's what
each one *means as an engineering decision* in this stack, so "explainable
intelligence" isn't just a value statement:

| Principle | Concrete mechanism |
|---|---|
| Data is a Product | Every table in ARC-004.1 gets an owning module, a documented lifecycle/retention policy (ARC-004.9), and a listed consumer set — enforced by doc review, not tooling, at this scale |
| Events are Immutable | `events` table has no `UPDATE`/`DELETE` grants for the application role; corrections are new events with a `correctsEventId` pointer |
| Relationships are First-Class | `entity_edges` is a top-level, independently queryable table — not something inferred by joining five other tables at query time |
| Operational/Analytical Separation | Analytics queries run against the logical-replication replica, never the primary — a slow dashboard query cannot degrade a cadre's task submission |
| AI Consumes Context, Not Raw Tables | A `ContextAssemblyService` (extends the existing `AiModule`) composes event history + graph edges + vector matches + current state into one structured object before it reaches Claude — no controller hands raw Prisma rows to a prompt |
| Multi-Tenancy by Design | §2 above: RLS-enforced `organizationId` on every tenant-scoped table |
| Explainable Intelligence | Every `AIInsight` gains `sourceEventIds[]` and `sourceEdgeIds[]` fields — a recommendation must cite the events and relationships it was derived from |
| Security by Default | RLS (isolation) + `RolesGuard`/`RegionScopeGuard` (authorization) + encryption at rest for PII columns (`Citizen.phone`, `Citizen.address`, `User.phone`, `User.email`) — detailed in ARC-004.9 |
| Scalable Evolution | The graduation triggers in §3's table exist precisely so a new domain (e.g. a future non-political-campaign tenant) doesn't require a new core model |
| Intelligence Over Information | The Digital Twin and predictive-intelligence deliverables (ARC-004.8, referenced by ARC-004.10) are the measure of success for this phase — not table count |

## 6. Governance, Briefly

Full detail is ARC-004.9's job; three things are non-negotiable starting now,
because they're much cheaper to build in than to retrofit:

- **PII is flagged at the schema level.** `Citizen.phone/address`, `User.phone/email`,
  `Grievance.description/photos` are personal data under India's DPDP Act 2023.
  ARC-004.1 must tag these fields; ARC-004.9 defines encryption and retention.
- **Every table has a named owner module** from the day it's added to the schema —
  matching the existing `/modules` structure (`docs/campaign-management-design.md` §3).
- **Lineage starts at the event.** Because every state change is an event (§4),
  lineage for any derived record (an embedding, a graph edge, a warehouse row) is
  "which event produced this" — not a separately maintained lineage system.

## 7. Non-Goals for Phase 2

Named explicitly so scope doesn't creep silently:

- **No Kafka, no Debezium, no managed vector DB, no Neo4j** unless and until a
  graduation trigger in §3 fires. Phase 2 delivers the *roles*, not a
  pre-emptive infrastructure buildout.
- **No cross-organization analytics or benchmarking** in Phase 2. Multi-tenancy
  in §2 is about isolation; platform-wide aggregate insight (e.g. "how does org A's
  campaign velocity compare to the platform average") is an explicit future
  capability, not part of this phase, and would need its own governance review
  before touching tenant data that way.
- **No autonomous agent actions.** ARC-004.10 covers how the data platform *powers*
  AI agents; agents taking write actions without a human in the loop is out of
  scope for Phase 2 regardless of what the data layer can support.
- **No physical multi-region deployment.** The isolation tiers in §2 allow for it
  later; Phase 2 targets one region.
